Documentation

The whole interface, on one sheet.

Everything below is the public surface. There is no hidden state, no clock, no file and no socket: a value goes in, bytes come out.

Install

moon add moonbitstack/moonfory

In moon.pkg:

import {
  "moonbitstack/moonfory",
}

The package is reached as @moonfory. Its dependencies are moonbitstack/moonvar for the numbers, moonbitstack/moondate for the time types and moonbitstack/moonmodel for the description of a struct; nothing else is pulled in.

The four verbs

A value goes in and comes out through dumps and loads. dump and load do the same over a Buffer or a Reader you already hold, for when a message is one part of a larger stream. 

// One value, all of it.
let message : Bytes = @moonfory.dumps(42)
let value : Int = @moonfory.loads(message)
assert_eq(value, 42)

// The same, without allocating a fresh buffer.
let sink = Buffer()
@moonfory.dump(value, sink)
let source = @moonfory.Reader::new(sink.to_bytes())
source.read_head()
let replayed : Int = @moonfory.load(source)
assert_eq(replayed, 42)
FunctionTakesGives
dumps(v, ...)any Codec valuethe message as Bytes
loads(b, schemas?, ...)a messagethe value, or a Refused
dump(v, buf, ...)a value and a bufferwrites into the buffer
load(r)a readerone value
write_message(w, v)a writer and a valuehead, value, nothing else
read_message(r)a readerthe one value the head announces
write_value(w, v) / read_value(r)a Valuethe dynamic form
One value, and then the end. loads reads exactly one value and then insists the message is finished. Two values in one buffer are a Trailing error, not a silent truncation.

Implementing Codec

A type joins in by implementing Codec. write_data writes the body only: the type ID belongs to whoever knows the schema, so a list element and a struct field each name their own type without the body repeating it. 

struct UserId(Int64)

pub impl @moonfory.Codec for UserId with fn ty(_self) -> @moonfory.TypeId {
  @moonfory.TypeId::Int64
}

pub impl @moonfory.Codec for UserId with fn write_data(
  self,
  w : @moonfory.Writer,
) -> Unit raise {
  w.write_i64(self.0)
}

pub impl @moonfory.Codec for UserId with fn read_data(
  r : @moonfory.Reader,
  _ty : @moonfory.TypeId,
) -> UserId raise {
  UserId(r.read_i64())
}

Bool, Int, Int64, UInt, UInt64, Byte, Float, Double, String, Bytes, Array[T], Map[K, V] and Value already implement it.

Strings are written as UTF-8. A reader also accepts LATIN1 and UTF-16, because pyfory writes LATIN1 for ASCII; only the writer's choice is fixed here.

Numbers, in one place

Int is written as INT32, Int64 as INT64, UInt as UINT32 and UInt64 as UINT64. The reader is looser on purpose: it accepts any width of the same signedness, so a peer's VARINT64 arrives as an Int without a byte of conversion. A 64-bit value asked for as a 32-bit type is refused rather than truncated.

Describing a struct

A struct's fields are a @moonmodel description — the same one an OpenAPI document or a CREATE TABLE would be generated from — plus the three things the wire needs that a description has no word for: the type ID the field goes out as, the tag that names it when the schema configures one, and whether the value may be shared. 

let point = @moonfory.StructMeta::new("Point", 100, [
  @moonfory.FieldMeta::new("x", @moonfory.TypeId::VarInt32),
  @moonfory.FieldMeta::new("y", @moonfory.TypeId::VarInt32),
])

let person = @moonfory.StructMeta::new("Person", 101, [
  @moonfory.FieldMeta::new("name", @moonfory.TypeId::String),
  @moonfory.FieldMeta::new("age", @moonfory.TypeId::VarInt32),
  // A list says what it holds, because the writer may leave the element type
  // out of the header.
  @moonfory.FieldMeta::new(
    "tags", @moonfory.TypeId::List, element=Some(@moonfory.TypeId::String),
  ),
  // A field whose type is declared sends no type ID, so the schema has to say
  // which struct it is.
  @moonfory.FieldMeta::new(
    "home", @moonfory.TypeId::Struct, nullable=true, child=Some(point),
  ),
])

A value writes its fields in Fory order whatever order it was given them in, and a reader hands them back in the order the schema declares them, so a value written and read again is equal to itself and writes the same bytes a second time.

From a #model.derive model, StructMeta::of fills the type IDs from the description's kinds and takes the child schemas by name; meta.model() hands the Model back, so one description can be published as a schema and used as a codec without being written twice. A kind with no wire type — Any — is refused rather than guessed at.

The fingerprint

Every struct carries a four-byte fingerprint of its schema and a peer checks it before it trusts a field: identifier,typeID,ref,nullable; per field in identifier order, hashed with MurmurHash3 x64 128 seeded with 47. A field of a user type writes 0 for its type ID and 0 for its ref flag, and a list writes its element as [type,0,0]. Under those rules the fingerprints here are the ones pyfory writes, byte for byte.

Precedence. A call has three places to say what it wants. The library preset (config) is the floor. A Config passed as config= replaces it wholesale. The flat mirrors — xlang=, track_ref=, check_string=, depth=, fields=, graph= — then override single fields of that result. When a Config and a flat mirror disagree, the flat mirror wins, unless wins=Base is passed, in which case the record wins. A disagreement is silent by default; clash=Warn(f) passes a line about it to f, clash=Panic aborts, and clash=Handle(f) lets you arbitrate. wins and clash are moonknob's, the same in every library of the family. 

// The preset, with one field changed.
let tracked = @moonfory.dumps(@moonfory.Value::Int(1L), track_ref=true)

// A whole config, with one field overridden on top of it.
let base = @moonfory.Config::new(depth=9)
let deeper = @moonfory.dumps(@moonfory.Value::Int(1L), config=base, depth=8)

// Two settings that disagree: taken as `wins` says, and reported.
let said : Array[String] = []
let reported = @moonfory.dumps(
  @moonfory.Value::Int(1L),
  config=base,
  xlang=false,
  clash=Warn(line => said.push(line)),
)
assert_eq(said.length(), 1)

Shared and circular values

MoonBit has no object identity to track, so identity is a key you choose and the value carries: Shared(key, value) is the value filed under that key, and Pointer(key) is the value already filed under it. The first is written out in full; the second is two bytes. 

let node = @moonfory.StructMeta::new("Node", 300, [
  @moonfory.FieldMeta::new("val", @moonfory.TypeId::VarInt32),
  @moonfory.FieldMeta::new("next", @moonfory.TypeId::Struct, track_ref=true),
])

// A node whose `next` is itself. Reference zero is the root, which this is.
let cyclic = @moonfory.Value::Struct(node, [
  ("val", @moonfory.Value::Int(1L)),
  ("next", @moonfory.Value::Pointer(0)),
])

let cyclic_bytes = @moonfory.dumps(cyclic, track_ref=true)
assert_eq(
  cyclic_bytes, b"\x01\x00\x1b\xac\x02\xee\xcb\x23\x4f\x02\xfe\x00",
)

Those are the bytes Go's fory writes for struct Node { Val int32; Next *Node }, byte for byte, and Go reads them back into a struct whose Next is itself. A value read from a peer is the same shape — the node it starts at is a Shared, and the field leading back to it is a Pointer — so it can be held without holding itself and sent again unchanged. 

let once = @moonfory.shared(7, "the same string")
let twice = [once, once] // two references, one body
let shared_bytes = @moonfory.dumps(twice, track_ref=true)
let shared_back : Array[@moonfory.Shared[String]] = @moonfory.loads(
  shared_bytes, track_ref=true,
)
assert_eq(shared_back.length(), 2)
assert_eq(shared_back[1].value, "the same string")

Turn track_ref on for both ends, or neither: a reader that is not tracking reads the first body and then a flag it does not expect. Python's pyfory cannot write a cycle at all — its serializer recurses — so Go is the peer the cyclic fixtures are checked against.

Interop, as a test

Every class of message here has been read from bytes another implementation wrote, and the bytes that go the other way have been read by that implementation: pyfory for Python and fory for Go. The fixtures are generated by scripts/interop.py and scripts/interop.go, run by hand, and checked in as MoonBit files the tests read — so CI runs the tests and needs neither language installed. 

python3 scripts/interop.py   # src/fixtures_pyfory_test.mbt
cd scripts && go run .         # src/fixtures_go_test.mbt
moon fmt

A fixture is the bytes and nothing else, and the MoonBit side says what the value is; the expectation for each one is written out by hand, because a test that could be made to pass by changing both sides at once is not one.

Three things the fixtures found. A nested struct goes out as its fingerprint and its fields with no type ID in front; a list whose element type the schema declares goes out without the type in its header; and a dense array goes out as a byte count and raw elements rather than as a list.

The row format

The row format trades a little space for random access: eight bytes per field, whether the field needs them or not, so field i is always at bitmap + i × 8. A reader takes one field and leaves the rest alone. 

let schema = @moonfory.RowSchema::new([
  { name: "id", ty: @moonfory.RowType::Int64, nullable: false },
  { name: "name", ty: @moonfory.RowType::String, nullable: false },
  { name: "age", ty: @moonfory.RowType::Int32, nullable: true },
])

let row = @moonfory.Row::new(schema)
row.set(0, @moonfory.RowValue::Int64(7L))
row.set(1, @moonfory.RowValue::String("ada"))
row.set(2, @moonfory.RowValue::Null)

let row_bytes = row.finish()
let cur = @moonfory.RowCursor::new(row_bytes[:], schema)
assert_eq(cur.get_field(1), @moonfory.RowValue::String("ada"))
assert_eq(cur.is_null(2), true)

The layout is the specification's standard variant: a null bitmap rounded to eight bytes, one eight-byte slot per field, then the variable data. An array keeps fixed-width elements at their natural width and variable ones as offset-and-size pairs; a map is a key array and a value array; a nested struct is a whole row inside the variable region.

The compact variant is not here. It is Java-only, so a cross-language implementation has no peer to agree with.

Time

Through moonbitstack/moondate, so a MoonBit program never spells out epoch seconds: 

let date = @moonfory.date_of_days(19_000L)
let moment = @moonfory.moment_of_parts(1_700_000_000L, 0)
let span = @moonfory.span_of_parts(3L, 500_000_000)

assert_eq(
  @moonfory.days_of_date(@moonfory.loads(@moonfory.dumps(date))), 19_000L,
)
let (seconds, nanos) = @moonfory.parts_of_span(
  @moonfory.loads(@moonfory.dumps(span)),
)
assert_eq(seconds, 3L)
assert_eq(nanos, 500_000_000)
let (epoch, _) = @moonfory.parts_of_moment(
  @moonfory.loads(@moonfory.dumps(moment)),
)
assert_eq(epoch, 1_700_000_000L)

Nanoseconds are always the sub-second part, in [0, 1e9), so a value of 1.5 seconds is (1, 500_000_000) and a negative span borrows a second rather than carrying a negative nanosecond field.
